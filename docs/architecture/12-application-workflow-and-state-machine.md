# 12. Application workflow and state machine

Status: ARCHITECTURE (design, not research). Derived from brief sections 24, 30, 31, 32, 64, 65, 66, 110–112.

## 12.1 Design principles

1. **The portal is the system of record.** WhatsApp, email and phone are channels; every state change is written to the application record.
2. **No silent submission.** A university submission can only occur from the `STUDENT_APPROVED` state and only after an explicit, time-stamped authorisation (section 12.6).
3. **Resumable by construction.** Every form step persists on change (autosave) and the application is addressable by its application number; "restart" is not a concept in the UI.
4. **Humans decide eligibility and admissions; the system reminds, collects, validates, tracks.** (Brief section 66.)
5. **Configurable order of payment and submission.** Different university arrangements may require payment before review, or review before payment. The order is a per-service-tier configuration, not hard-coded.
6. **Every transition is an event.** Events drive notifications, dashboard "next action", analytics and audit.

## 12.2 Application number

Format: `SMN-{intake_year}-{6-digit sequence}` → e.g. `SMN-2027-000123`.

- `intake_year` = the academic year of intended entry chosen by the student (not the year of registration).
- Sequence is global, zero-padded, never reused. Generated by the database (sequence/auto-increment) at `APPLICATION_STARTED`, never client-side.
- Shown in: portal header, every email subject, Stripe metadata (`application_number`), document filenames in storage, admin lists, submission package cover sheet.

## 12.3 Entities and their own lifecycles

There are **three** state machines, not one. Collapsing them (as the brief's linear list implies) causes the classic bug where "documents incomplete" and "payment required" fight over a single status field.

| Entity | Owns | Status field |
|---|---|---|
| `Application` | the student's journey with us | `application.stage` (12.4) |
| `Document` (per required item) | one requested file | `document.status` (14.x) |
| `Payment` (per Stripe session) | money | `payment.status` (15.x) |
| `Submission` (per university/course target) | one university application package | `submission.status` (16.x) |

`Application.stage` is **derived** where possible (e.g. `DOCUMENTS_COMPLETE` becomes true when every required Document is `ACCEPTED`), and **explicitly set by staff** only for judgement states (`INTERNAL_REVIEW`, `ACTION_REQUIRED`, `READY_FOR_STUDENT_APPROVAL`).

## 12.4 Application stages (configurable list; default order)

```
LEAD
  └─ ACCOUNT_CREATED
       └─ APPLICATION_STARTED
            └─ APPLICATION_INCOMPLETE        (derived: any required form section not complete)
                 └─ APPLICATION_COMPLETE     (derived: all required form sections complete)
                      └─ DOCUMENTS_INCOMPLETE (derived: any required Document not ACCEPTED)
                           └─ DOCUMENTS_COMPLETE (derived)
                                └─ INTERNAL_REVIEW        (staff)
                                     ├─ ACTION_REQUIRED    (staff → student; loops back to INCOMPLETE states)
                                     └─ READY_FOR_STUDENT_APPROVAL (staff; requires ≥1 Submission target defined)
                                          └─ STUDENT_APPROVED        (student action; records authorisation)
                                               └─ PAYMENT_REQUIRED    (derived: tier requires payment not yet COMPLETE)*
                                                    └─ PAYMENT_COMPLETE (derived from Payment)
                                                         └─ READY_FOR_UNIVERSITY_SUBMISSION (derived: approved + paid + package built)
                                                              └─ SUBMITTED                 (from Submission)
                                                                   └─ UNIVERSITY_ACKNOWLEDGED
                                                                        └─ INTERVIEW | OFFER | REJECTED | WAITLIST | OTHER_STAGE
                                                                             └─ COMPLETED
Side states (any time): WITHDRAWN (student), CLOSED (staff, with reason), ON_HOLD (staff, with reason + review date)
```

\* **Payment position is configurable per service tier** (`tier.payment_gate`):
- `AT_START` — payment is required before the application form opens (Tier 1 and Tier 2 default; the service *is* the assessment/preparation, so work cannot begin unpaid).
- `BEFORE_REVIEW` — form and documents can be completed free; payment unlocks `INTERNAL_REVIEW`.
- `BEFORE_SUBMISSION` — payment required only after `STUDENT_APPROVED` (shown in the default diagram; suits a Tier 3 arrangement where the student wants to see the proposed submission before paying the submission component).

The derived stage is computed by a single pure function `deriveStage(application, documents, payments, submissions, tier)` so that the dashboard, emails and admin always agree.

## 12.5 Transition rules (who may cause each transition)

| From → To | Actor | Guard | Side-effects (events) |
|---|---|---|---|
| (none) → LEAD | system | lead form or eligibility quiz submitted | `lead.created` → staff notification, welcome email (if consented) |
| LEAD → ACCOUNT_CREATED | student | email verified | `account.created` |
| ACCOUNT_CREATED → APPLICATION_STARTED | student | tier selected; if `payment_gate=AT_START` then Payment COMPLETE | `application.started`; application number issued; document checklist generated (14.3) |
| → APPLICATION_COMPLETE | derived | all required sections valid | `application.completed` → staff |
| → DOCUMENTS_COMPLETE | derived | all required Documents ACCEPTED | `documents.completed` → staff |
| DOCUMENTS_COMPLETE → INTERNAL_REVIEW | staff (or auto-assign) | — | `review.started` |
| INTERNAL_REVIEW → ACTION_REQUIRED | staff | at least one request raised (document request or form correction) | `action.required` → student email + dashboard banner |
| ACTION_REQUIRED → INTERNAL_REVIEW | derived | all open requests resolved | `action.resolved` → staff |
| INTERNAL_REVIEW → READY_FOR_STUDENT_APPROVAL | staff | ≥1 Submission target with university, course, intake, route set; package preview renders | `approval.requested` → student email "Please approve your application" |
| READY_FOR_STUDENT_APPROVAL → STUDENT_APPROVED | **student only** | authorisation checkbox + typed name; records snapshot (12.6) | `student.approved` → staff; `Submission.status = AUTHORISED` |
| READY_FOR_STUDENT_APPROVAL → ACTION_REQUIRED | student | "Request changes" with free text | `approval.declined` → staff |
| → PAYMENT_COMPLETE | Stripe webhook | `checkout.session.completed` verified | `payment.succeeded` → receipt email |
| → READY_FOR_UNIVERSITY_SUBMISSION | derived | approved + (paid or no payment gate) + package built | staff notification |
| → SUBMITTED | staff | Submission marked submitted with method + reference (16.x) | `submission.sent` → student email |
| SUBMITTED → UNIVERSITY_ACKNOWLEDGED → … | staff | each update carries a note and optional document (e.g. offer letter) | `university.response` → student |
| any → WITHDRAWN | student | confirm dialog | `application.withdrawn` → staff; stops reminders |
| any → ON_HOLD / CLOSED | staff | reason required | reminders paused/stopped |

**Invariants enforced in code, not policy:**
- `Submission.status` can become `SUBMITTED` only if `Submission.authorisation_id` is not null.
- `Authorisation.snapshot_hash` must equal the hash of the current package; if the package changes after approval (new document version, edited field), the authorisation is **invalidated** and the stage returns to `READY_FOR_STUDENT_APPROVAL` with a clear message. No stale approvals.
- Students cannot edit sections included in an active authorisation without explicitly revoking it.

## 12.6 Student authorisation record

Captured at `STUDENT_APPROVED`:

```
authorisation {
  id, application_id, submission_id,
  approved_at (UTC), approved_by_user_id, ip_address, user_agent,
  declaration_text_version,          // the exact wording shown, versioned
  typed_name,                        // student types full name
  snapshot_hash,                     // SHA-256 of canonical JSON of package
  snapshot_json,                     // frozen copy: form data, document ids+versions, target university/course/intake, service tier, fee status
  revoked_at, revoked_reason         // null unless revoked
}
```

Declaration text (v1):
> I have reviewed the information and documents shown above. I confirm they are accurate and complete to the best of my knowledge. I authorise StudyMedicineUKNigeria to prepare and submit, or to guide me to submit, this application to **{university} — {course} ({intake})** by the route described. I understand that admission decisions are made solely by the university, that no admission, scholarship or visa outcome is guaranteed, and that university fees are separate from any service fee I have paid.

## 12.7 "Next action" engine

The dashboard's single most important line is computed by `nextAction(application)`:

1. If `stage ∈ {READY_FOR_STUDENT_APPROVAL}` → "Review and approve your application" → `/portal/approve`.
2. Else if `payment_gate` blocks progress and no COMPLETE payment → "Complete payment for {tier}" → `/portal/payments`.
3. Else if any Document `status ∈ {REQUIRED, REPLACEMENT_REQUIRED}` → "Upload your {document name}" (earliest requested first) → `/portal/documents/{id}`.
4. Else if any form section incomplete → "Continue: {section name}" → the step URL.
5. Else if `stage ∈ {INTERNAL_REVIEW}` → "We are reviewing your file. Nothing needed from you. Typical review time: {configured}."
6. Else if `stage ∈ {SUBMITTED, UNIVERSITY_ACKNOWLEDGED}` → "Submitted to {university} on {date}. We will update you when the university responds."
7. Else → stage-specific copy.

Completion percentage = weighted: form sections 50%, documents 40%, approval 10%. Weights are config.

## 12.8 Lead execution sequence (automation map)

| Step | Automated? | Mechanism |
|---|---|---|
| Lead captured (eligibility check or Apply Online) | yes | form → `leads` table → staff email/Slack-style digest |
| Account creation prompt | yes | immediate CTA + email with magic link |
| Service tier recommendation | **assisted** | rule-based suggestion from eligibility answers (e.g. no A-levels/IB → suggest Tier 1 assessment first); staff can override; copy says "suggested", never "you are eligible" |
| Payment | yes | Stripe Checkout (15.x) |
| Application creation + number | yes | at `APPLICATION_STARTED` |
| Document checklist | yes | rules engine (14.3) |
| Reminders | yes | scheduler: incomplete after 2, 7, 14, 30 days; document requested after 3, 10 days; approval requested after 2, 7 days; stop on WITHDRAWN/CLOSED/ON_HOLD; max 1 email/48h per application |
| Internal review | **human** | staff queue |
| Eligibility judgement | **human** | staff notes; portal shows staff-written outcome |
| Student approval | **human (student)** | 12.6 |
| Package preparation | yes (PDF cover sheet + ordered documents) | 16.x |
| Submission | **human** (staff) or **student-guided** (UCAS) | 16.x |
| Status updates to student | yes | events → emails |

## 12.9 Reporting events (for GA4 / internal dashboard)

`lead_created`, `account_created`, `application_started`, `step_completed{step}`, `document_uploaded{type}`, `document_accepted`, `document_rejected`, `payment_started{tier}`, `payment_completed{tier}`, `approval_requested`, `student_approved`, `submitted{route}`, `university_response{type}`. Each carries `application_number` hashed, `tier`, `intake_year`, `country=NG` where consented.
