## 5. Rollback safety (designed and proven 2026-10-30)

**[Fact] The problem.** A code rollback (manual, or automatic after a failed smoke test) used to switch back to `5d76858` and leave the 30 imported fact decisions in the database. The old code has no register gate. On the production mirror it then served **47 URLs**: 11 more than before the deploy, namely the cost page, Aberdeen, Buckingham and the nine RESEARCH schools. Preventing that relied on someone remembering to unpublish schools.

**[Fact] The design (no manual step):**

1. **Deploy.** `ops/deploy.sh` runs `ops/import-decisions.sh`. It imports every committed decision file and writes the files this release actually applied to `<release>/.facts-imported`; files already in the ledger are skipped.
2. **Rollback, both paths.** Before switching code, `ops/revert-release-facts.sh <release>` runs, with the abandoned release's own code. For each file in that list, newest first, `php artisan smukn:facts-revert <file>` runs:
   - it restores every fact that still holds the imported values to its previous values, from `fact_changes`;
   - it keeps any fact changed since (the watcher, an admin) and reports it;
   - it removes the file's `fact_imports` ledger row, so a redeploy applies the file again;
   - it records every revert in `fact_changes`.

   The two paths are *Roll back Hostinger release* (`ops/rollback.sh`) and the deploy's automatic rollback after a failed smoke test.
3. **Releases without a list** (all earlier ones) have nothing to undo, and the revert is skipped.
4. **If the revert fails,** the code rollback still happens, because the reason to roll back may be a broken release, but the run fails loudly with the exact manual command. `revert_facts` = `false` on the rollback workflow skips the revert deliberately; it defaults to `true`.

**[Fact] Proof on the production mirror** (`ops/qa/rollback-proof/run.sh`; the live release's code as a git worktree of `5d76858`):

| Step | Result |
|---|---|
| 1. Mirror of production (state of 05:38 UTC today) | built; 151/153 flags; 39 published schools |
| 2. Live code on the mirror | 36 URLs = live sitemap, 0 differences |
| 3. Deploy steps with this branch (`reference-sync`, `ops/import-decisions.sh`) | 4 files applied (2 + 2 + 23 + 3 facts); all 4 recorded for rollback |
| 4. This branch after the deploy | 39 URLs; robots and canonical as in §3 |
| 5. Failure mode: code rollback without the revert | old code serves **47** URLs |
| 6. Rollback with `ops/revert-release-facts.sh`, then old code | 30 facts restored, 0 kept; **36 URLs, 0 differences** from before the deploy; **reference_facts identical (0 of 826 rows differ)**; `fact_imports` ledger identical; 30 revert entries in `fact_changes` |
| 7. Redeploy after the rollback | 4 files applied again; 39 URLs, identical to step 4 |

**[Fact] End-to-end run of the real `ops/rollback.sh`** on a copy of the mirror after step 4, with a stand-in `ssh` that runs the remote script locally (releases A = `5d76858`, B = this branch): 30 facts restored, `current` switched B → A, exit 0; the old code then served **36 URLs, 0 differences**, and 0 fact rows differed from before the deploy. If the revert fails, the script still switches code and runs the smoke test, then exits 4 with the manual command.

**[Fact] Not covered by the revert:**
- Anything else a release might change in the database. This release has no migrations, and `reference-sync` produced no new rows on the mirror.
- **Student or staff data written after the deploy is never touched.** A full database restore stays a deliberate step (`ops/RESTORE.md`, the dump `~/backups/production-db-<timestamp>.sql.gz` taken before `migrate`).
